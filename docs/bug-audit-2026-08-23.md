# 一、致命（2）

## 1. Win32Canvas 析构双重释放 currentFont_ 【致命·内存安全】✅

**位置**：`src/platform/win32/win32_canvas.cpp:49, 55-56, 112-117, 119-150`

`currentFont_` 永远指向 `fontCache_` 持有的对象（`setFont()` 两个返回路径均来自缓存），
析构函数先 `delete currentFont_` 再遍历 `fontCache_` 删除同一指针 → double free（堆损坏，
通常表现为退出时崩溃）。

```cpp
Win32Canvas::~Win32Canvas() {
  delete backbuffer_;
  delete graphics_;
  delete currentFont_;              // ← 与 fontCache_ 中的指针相同
  ...
  for (auto &pair : fontCache_)
    delete pair.second;             // ← 同一指针第二次 delete
}
```

**建议**：删除析构中的 `delete currentFont_;` 一行（`currentFont_` 只是缓存指针的别名）；
或改为 `std::unique_ptr` + 缓存持裸指针的架构。任何一次 `setFont()` 后销毁窗口即触发。

## 2. Cocoa 关闭窗口无限递归 → 栈溢出 【致命·逻辑错误】✅

**位置**：`src/platform/cocoa/cocoa_window.mm:28-32, 261-265`；
链路：`src/app.cpp:176`、`src/window.cpp:93-97, 189-194`

`windowShouldClose:` 恒返回 NO，同时调 `onClose()`；`close()` 走 `performClose:`。
完整闭环：点击红色关闭按钮（或任何 `close()`）→ `windowShouldClose:` → `onClose()` →
`eventCallback_(Close)` → `Window::handleCloseEvent` → `Application::closeWindow(this)` →
`window->close()`（app.cpp:176，走的是 `close()` 不是 `destroy()`）→ `performClose:` →
再次 `windowShouldClose:`……`cppWindow_` 全程非空，无人打断，无限递归直至栈溢出。
macOS 上关闭窗口即崩溃。

```objc
- (BOOL)windowShouldClose:(NSWindow *)sender {
  if (cppWindow_)
    cppWindow_->onClose();
  return NO;          // 否决关闭 → close 永不完成
}
void CocoaWindow::close() {
  if (nsWindow_)
    [nsWindow_ performClose:nil];   // 回到 windowShouldClose
}
```

**建议**：`windowShouldClose:` 返回 YES（关闭完成后发 Close 事件），或
`CocoaWindow::close()` 仿照 X11 端直接 `orderOut:`/销毁而不走 `performClose:`，打破闭环。

# 二、高（23）

## 3. 焦点控件被摘除后销毁 → focusWidget_ 悬垂指针 UAF 【高·内存安全】✅

**位置**：`src/widget.cpp:33-39, 70-83`；`src/window.cpp:213-214, 292-306`

`removeChild()` 调 `propagateWindow(nullptr)` 把 `window_` 置空；之后销毁该控件时
`~Widget` 因 `window_ == nullptr` 跳过焦点清理，`Window::focusWidget_` 成为悬垂指针。
下次 `validateFocusWidget()`（解引用 `focusWidget_->window()`）或 Tab 键
（`window.cpp:213-214` 在 validate 之前直接解引用）即 UAF。

```cpp
Widget::~Widget() {
  if (window_ && window_->focusWidget_ == this) {   // window_ 已被清空 → 跳过
    window_->setFocusWidget(nullptr);
  }
}
// removeChild:
(*it)->propagateWindow(nullptr);   // 只清 widget 侧指针，未通知 Window
```

**建议**：在 `propagateWindow(nullptr)`（或 `removeChild`）中，若该控件是窗口焦点则同步
`window_->setFocusWidget(nullptr)`，使析构清理不依赖 `window_` 非空。

## 4. dispatchSnapshot_ 共享成员缓冲区，模态对话框嵌套泵事件导致迭代器失效 UB 【高·内存安全】✅

**位置**：`src/widget.cpp:421-468`；触发路径 `src/widgets/dialog.cpp:57-66`

`dispatchToChildren` 把子控件快照存进**成员** `dispatchSnapshot_` 而非局部变量。按钮
onClick 槽内 `MessageBox::show()` → `Dialog::exec()` 嵌套泵取平台事件时，新事件再次进入
**同一个**根控件的 `dispatchToChildren`，其 `snapshot.clear()` 使外层循环正在使用的
reverse_iterator 失效，外层循环恢复时是未定义行为。

```cpp
auto &snapshot = dispatchSnapshot_;   // 共享成员，非局部
snapshot.clear();
...
for (auto it = snapshot.rbegin(); it != snapshot.rend(); ++it) { ... }
// 槽内嵌套 pump → 同成员 clear() → 外层 it 失效
```

**建议**：改为每次调用的局部 `std::vector<Widget*>`（或递归深度感知的栈式缓冲）。

## 5. Signal::emit 槽函数销毁所有者 → UAF 【高·内存安全】✅

**位置**：`include/ltgui/signal.h:152-199`

槽函数在 emit 过程中销毁拥有该 Signal 的对象（GUI 中最常见模式：点击按钮关闭对话框）
时，`slots_`/`pendingSlots_` 随 Signal 一起析构；循环内后续 `slots_[i]` 与收尾的
`compactSlots()` 都是对已释放内存的读写。第 18-21 行注释声称 shared_ptr 防 UAF，但
`emitting_` 的 shared_ptr 只保住 bool 控制块，保不住槽列表。

```cpp
size_t count = slots_.size();
for (size_t i = 0; i < count; ++i) {
  auto &slot = slots_[i];           // 前一个槽 delete 了所有者 → 本行 UAF
  if (slot.cb)
    slot.cb(args...);               // 槽内销毁 Signal 所有者
}
if (!pendingSlots_.empty()) { ... compactSlots(); }   // 已析构对象上调用
```

**建议**：把槽列表（连同 emitting_ 状态）放入 shared_ptr 状态块，emit 期间持有局部
引用；或文档明确禁止并检测 emit 期间销毁 Signal 自身。

## 6. TextBox 鼠标定位光标落在 UTF-8 字符中间 → 文本损坏 【高·逻辑错误】✅

**位置**：`src/widgets/textbox.cpp:372-384, 400-408`

点击/拖动定位光标用字节级二分查找，`lo` 可能落在多字节字符（如中文 3 字节）中间；
随后 `insert`/`erase`/IME 预编辑从字符中间劈开，文本损坏（乱码/丢失）。

```cpp
int lo = 0, hi = static_cast<int>(text_.size());
while (lo < hi) {
  int mid = (lo + hi) / 2;                       // 任意字节偏移
  int w = can->measureText(text_.substr(0, mid)).width;
  ...
}
cursorPos_ = lo;   // 未对齐字符边界
```

**建议**：二分查找后对 `lo` 用 `utf8::nextPos(text_, lo)` 对齐到下一字符边界（或比较时
只取边界位置）。

## 7. TextBox 无 FocusIn 处理 → Tab/程序获焦后无法打字、光标不显示 【高·逻辑错误】✅

**位置**：`src/widgets/textbox.cpp:354-462`；`src/window.cpp:322-326`

TextBox 私有 `focused_` 只在 MouseDown 里被置 true，从不处理 FocusIn 事件。Window 在
`setFocusWidget` 时会向新焦点控件发 FocusIn，但 TextBox 的 switch 里只有 FocusOut。
Tab 键或 `claimFocus()` 获焦后 `focused_` 保持 false：光标不绘制，
`KeyDown` 的 `if (focused_)` 入口守卫（textbox.cpp:440）拦截全部键盘输入——必须先用
鼠标点一下才能打字。

**建议**：增加 `case EventType::FocusIn: focused_ = true; update(); return true;`。

## 8. utf8::nextPos 对截断序列返回越界位置 → substr/insert 抛异常崩溃 【高·边界越界】✅
（B2-08 与 B3-07 合并）

**位置**：`include/ltgui/utf8.h:72-77`；触发点 `src/widgets/textbox.cpp:345, 110, 154`

对以截断多字节前导字节结尾的字符串（如粘贴产生的非法 UTF-8），`nextPos` 返回超过
`s.size()` 的位置。例如 `text="ab\xF0"`（长度 4），pos=3 时返回 3+4=7。随后
`displayText.substr(0, displayCursor)` 抛 `std::out_of_range`，事件/绘制路径无捕获，
直接终止进程。

```cpp
inline int nextPos(const std::string &s, int pos) {
  int len = static_cast<int>(s.size());
  if (pos < 0 || pos >= len)
    return len;
  return pos + codePointLen(static_cast<unsigned char>(s[pos]));  // 可 > len
}
```

**建议**：`return std::min(len, pos + codePointLen(...));`；同时 TextBox 在使用前
clamp `cursorPos_` 到 `[0, text_.size()]`。

## 9. 绘制过程中产生的 update() 失效被双层丢弃 → 残影/内容不更新 【高·逻辑错误】✅
（B1-08 与 B6-03 合并）

**位置**：`src/window.cpp:163-177`；`src/platform/win32/win32_window.cpp:262-269`

`onPaint`（含 paintSelf）期间控件调用 `update()` → `Window::invalidate` 置
`dirtyValid_=true` 并 `InvalidateRect`。但 `handlePaintEvent` 在 `endPaint` 后无条件
`dirtyValid_ = false` 抹掉累积失效；随后 Win32 的 WM_PAINT 处理器再
`ValidateRect(hwnd_, nullptr)` 把 OS 更新区域一并清掉——不再有 WM_PAINT，这次绘制请求
永久丢失。动画/悬停/布局变化引起的重绘会随机失效。

```cpp
// window.cpp:169-175
onPaint(canvas_, accumulatedDirty_);   // 期间 update() → dirtyValid_=true
canvas_->endPaint();
dirtyValid_ = false;                   // 丢弃 onPaint 期间累积的失效
// win32_window.cpp:268
ValidateRect(hwnd_, nullptr);          // 连同新失效区一并清除
```

**建议**：在 `endPaint` 前（而非之后）清除 `dirtyValid_`；平台层只
`ValidateRect` 本次实际绘制的区域（标准做法是 BeginPaint/EndPaint 配对）。

## 10. Dialog 模态体系整体不可用——exec() 立即返回 None 【高·逻辑错误】✅

**位置**：`src/widgets/dialog.cpp:16, 35-49, 200-209, 253-263`；`src/widget.cpp:10, 243-250`

`Widget(parent)` 构造函数只存 `parent_` 指针，不加入父控件 children；
`window_` 只由 `propagateWindow`（addChild/setCentralWidget 链路）赋值。
`MessageBox::show`/`InputDialog::getText` 均裸构造对话框，从不 `addChild` 入树，
`window()` 恒为 nullptr，`exec()` 在第 46-48 行直接返回 `DialogResult::None`——
对话框不显示、事件循环不运行、`claimFocus()` 也是空操作。dialog.h 声称的
"Window 检测并重定向事件到活动对话框" 在整个 window.cpp 中不存在（grep 零匹配）。

```cpp
// dialog.cpp:45-49
auto *win = window();
if (!win) {
  running_ = false;
  return DialogResult::None;   // 所有真实用法都走这里
}
// dialog.cpp:204
MessageBox mb(parent);   // 裸构造，不入树
```

**建议**：`exec()` 内部通过父控件链找到 Window 并把对话框挂入树中（或 Window 层新增
模态弹层机制），在 Window 事件入口对运行中的模态对话框做重定向与遮罩点击拦截。

## 11. MenuBar 下拉菜单画在自身几何之外 → 鼠标永远点不到 【高·逻辑错误】

**位置**：`src/widgets/menubar.cpp:280-316, 496-501`；`src/window.cpp:236-264`；
`src/widget.cpp:442-448`

下拉面板和子菜单直接用 canvas 画在菜单栏矩形之外（`dropY = r.bottom()`），它们不是
子控件，`effectiveGeometry()` 只覆盖菜单栏条本身。MouseDown 是定向分发（只发给命中
测试区域内的控件），下拉区域的点击永远到不了 MenuBar；点击别处也不会关闭已打开的
菜单。window.cpp 只对 ComboBox（`openCombo_`）做了下拉区特殊路由，MenuBar 无对应处理。
现有测试直接对 MenuBar 调 `handleEvent` 发键盘事件，绕过了 Window 分发，测不出此问题。

**建议**：参照 ComboBox 在 Window 层增加"打开的菜单栏"状态，把打开期间的下拉区点击
路由给 MenuBar；`hitTestItem` 需结合 X 坐标判断是否落在子菜单区。

## 12. Dialog 不向子控件转发键盘 → InputDialog 无法输入文本 【高·逻辑错误】✅

**位置**：`src/widgets/dialog.cpp:138-146, 265-271`；`src/widget.cpp:470-486`

`exec()` 里 `claimFocus()` 让对话框自己获焦，而 `Widget::handleEvent` 只分发鼠标事件，
KeyDown 不转发给子控件 → InputDialog 的 TextBox 永远收不到字符。另外
`InputDialog::handleEvent` 对任何 Enter 都 `done(OK)`，即使焦点在 Cancel 按钮上。

**建议**：Dialog 把未消费的 KeyDown 转发给焦点子控件（或让 `input_` 在 exec 时获焦）；
Enter 仅在焦点不在 Cancel 类按钮上时提交。

## 13. WideCharToMultiByte off-by-one 越界写 1 字节 【高·内存安全】

**位置**：`src/platform/win32/win32_window.cpp:239-243`

`result.resize(len - 1)` 后仍以 `len`（含结尾 NUL）作为缓冲区大小调用
`WideCharToMultiByte`，写入比缓冲区长 1 字节。当 `len-1` 恰好等于容量时破坏堆。

```cpp
int len = WideCharToMultiByte(CP_UTF8, 0, p, -1, nullptr, 0, nullptr, nullptr);
if (len > 0) {
  result.resize(len - 1);
  WideCharToMultiByte(CP_UTF8, 0, p, -1, &result[0], len, ...);  // 写 len 字节进 len-1 缓冲区
}
```

**建议**：`result.resize(len)` 后 `result.pop_back()`，或传入 `len-1` 作为 cbMultiByte。

## 14. X11 SelectionRequest 未处理 property=None → BadAtom 杀进程 【高·X11 API 误用】

**位置**：`src/platform/x11/x11_window.cpp:462-471`

按 ICCCM，请求者可将 property 指定为 None（所有者应把数据写到名为 target 的
property）。对 None 调 `XChangeProperty` 产生 BadAtom 错误，Xlib 默认错误处理器直接
终止进程——其他程序的一个**合法**请求就能杀死本应用。

**建议**：写属性前判空：`Atom prop = (req.property == 0) ? req.target : req.property;`；
同时安装 `XSetErrorHandler` 兜底，避免任何 Bad* 错误退出进程。

## 15. Cocoa destroy() 被 windowShouldClose 否决 → 僵尸窗口 + MRC 三对象泄漏 【高·资源泄漏】✅

**位置**：`src/platform/cocoa/cocoa_window.mm:232-247`

`destroy()` 依赖 `[nsWindow_ close]` 关闭窗口，但委托恒返回 NO（见条目 2），close 被
否决——窗口永不消失，成为留在屏幕上的"僵尸窗口"。同时该文件以 MRC 编译（第 67 行
`[area release]` 为证），`nsWindow_`/`delegate_`/`view_` 只置空指针从不 `release`，
三个对象全部泄漏。

**建议**：先 `[delegate_ release]`；`[nsWindow_ orderOut:nil]`（或让委托在
`cppWindow_ == nullptr` 时返回 YES）；再 `[nsWindow_ release]`、`[view_ release]`。

## 16. Cocoa keyDown:/keyUp: 无 cppWindow_ 空指针守卫 → 销毁后按键崩溃 【高·内存安全】✅

**位置**：`src/platform/cocoa/cocoa_window.mm:141-177`

`keyDown:`/`keyUp:` 是仅有的两个不检查 `cppWindow_` 是否为空的输入处理器（mouseDown/
mouseMoved/scrollWheel 均有守卫）。`destroy()` 已把 `view_->cppWindow_` 置空，而按

## 19. 字形缓存 key 丢弃 size/weight/style → 同族不同字号字形互相污染 【高·逻辑错误】✅

**位置**：`src/platform/gpu/gpu_font_atlas.cpp:97, 369-375`

style XOR 在返回值 bit32~55，左移 32 位后这些位全部被移出丢弃，key 实际只含
family 哈希的低 32 位 + 码点。同一 family 下 12px 先缓存后，24px（或 Bold/Italic）

```cpp

```

**建议**：key 直接使用完整 `fontKey` 与 codepoint 的 64 位混合（如
`fontKey ^ (codepoint * 0x9E3779B97F4A7C15ULL)`），保证 size/weight/style 参与键值。

## 42. TableView 模型行数收缩后 scrollY_/selectedRow_ 不钳制 → 视图全空白 【中·逻辑错误】

## 52. X11 剪贴板无 INCR：读截断 64KB、写失败不检查且无条件回复成功 【中·协议缺陷】

**位置**：`src/platform/x11/x11_window.cpp:262-299（读）、462-471（写）`

## 53. X11 非 ASCII 字符输入全部丢失 【中·逻辑错误】

**位置**：`src/platform/x11/x11_window.cpp:415-420`

ASCII 字符（中文、日文等）返回多字节序列（len > 1）被整体丢弃——X11 后端无法输入

# 五、修复路线图（建议）

## 第一阶段：致命 + 核心功能失效（建议优先）

1. **条目 1**：Win32Canvas 双重释放（一行修复）
2. **条目 2 + 15 + 16**：Cocoa 关闭窗口递归 + 僵尸窗口 + 空指针守卫（三处联动修复）
3. **条目 10 + 12**：Dialog 入树 + 键盘转发（模态体系整体不可用）
4. **条目 3 + 4 + 5**：三处 UAF（焦点悬垂、dispatch 快照重入、Signal emit）
5. **条目 6 + 7 + 8**：TextBox UTF-8 光标/越界/FocusIn（文本输入核心体验）
6. **条目 17**：Cocoa acceptsFirstResponder（macOS 键盘完全不可用）

## 第二阶段：功能正确性

- 条目 11（MenuBar 下拉不可点击）、14（X11 BadAtom 杀进程）、9（绘制失效丢失）、
  22-24（构建脚本）、25/63/64（i18n 复数规则）、18-21（GPU 泄漏/字形污染/描边垃圾）、
  52-53（X11 剪贴板/输入法）

## 第三阶段：状态机与边界

- 31-36（Signal 递归、动画计数泄漏、日志门控）、37-40（选区/单选/信号契约）、
  41-45（Tab/Table/Scroll 状态错乱）、50-51（DPI/光标）、54-58（Cocoa/GPU 资源与字节序）

## 工程建议

1. **补测试防回归**：现有测试全部通过是因为关键路径绕过了 Window 分发（MenuBar 键盘
   直调、Dialog 无窗口路径测不出）。建议补：真实窗口集成测试、Signal 重入测试、
   UTF-8 非法序列模糊测试、i18n 全语言复数断言。
2. **D3D11 debug layer 验证**：条目 21 的输入布局不匹配与条目 58 的红蓝颠倒需要
   真机运行验证；debug layer 会直接报告布局不匹配。
3. **Cocoa 后端建议直接迁移 ARC**：条目 54 的每帧泄漏与 15/16 的生命周期问题在 MRC
   下极易复发，迁移 ARC 可消除整类问题。
4. **X11 错误处理器**：条目 14/96 之外，任何 Bad* 错误都不应直接终止 GUI 进程，
   安装 `XSetErrorHandler` 应作为基础防御。
5. **构建脚本自检**：在 CI 中加一条「生成融合头并编译冒烟」步骤，防止
   `_HEADER_ORDER` 再次失同步（条目 22）。
